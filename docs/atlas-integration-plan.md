# Atlas 接入规划：可主动刷新的玩家查询与服务器匹配时间

日期：2026-11-08。状态：**规划稿，尚未实现，等待维护者决定第 5 节的问题。** 本稿只包含规划和已查明的使用规范，没有改动任何代码。

## 1. 目标

1. 用 [Atlas](https://www.eftforge.com/atlas) 的接口重做玩家数据查询，并支持主动刷新。
2. 新增服务器匹配时间查询（各数据中心的平均匹配等待时间）。
3. 在 README 的“特别致谢”里写明 Atlas（已完成）。

维护者说明：已获得 Atlas 开发者授予的 API 调用权限和刷新密钥。密钥不写进仓库、文档、测试、日志或聊天，只放在插件配置里（见 6.3）。

**Atlas 作者的补充（2026-11-08，已采用，优先于下文对公开代码的推断）：**

- 匹配时间接口 `https://eftforge.com/atlas/api/matching` 是公开的，可以直接使用；要求**做缓存，不要高频轮询**。
- **匹配时间和玩家查询都不需要密钥**，直接调用即可。
- 玩家查询按 IP 限流：**每分钟 20 次、每小时 200 次**。
- 可以在插件里做缓存和用户冷却；遇到 429 **按 `Retry-After` 等待**。
- **玩家查询的流程（作者确认）**：先 `https://eftforge.com/atlas/api/lookup/search?nickname=<昵称>` 搜索，再用 `https://eftforge.com/atlas/api/lookup?accountId=<账号ID>` 查询详情；两个接口都可以加 `mode` 参数（`season`、`pvp`、`pve`、`arena`），**不写时默认是 `season`**。
- 作者没有提到“刷新”接口，也没有说刷新密钥用在哪里，见 2.6。

## 2. 已查明的使用规范

### 2.1 证据来源和可信度

- 来源：EFTForge 公开仓库（`SouthHorizons76/EFTForge`，提交 `ca6da4b` “atlas key scopes”，2026-11-08），主要是 `backend/routers/atlas.py`、`backend/routers/atlas_lookup.py`、`backend/services/lookup_guard.py` 和前端 `frontend/modules/atlas-*.js`。
- 与“未公开源码”的出入：仓库里**有** Atlas 的网页后端，但它只是“转发层”。玩家数据由一个私有的上游提供方回答（环境变量 `ATLAS_LOOKUP_URL`），那部分的实现和刷新机制不在仓库里。下面写的是对外接口的约定，不是上游的内部行为。
- 局限：这是代码阅读的结果，没有对线上服务做过实测（本开发环境的网络策略目前拦截了 `eftforge.com`，见 6.4）；代码随时可能变。**最终以 Atlas 开发者给的说明为准。**

### 2.2 接口

| 用途 | 请求 | 说明 |
|---|---|---|
| 按昵称找人 | `GET /atlas/api/lookup/search?nickname=<名>&mode=<模式>` | 返回 `{nickname, players:[{accountId, nickname}]}` |
| 查一名玩家 | `GET /atlas/api/lookup?accountId=<数字>&mode=<模式>` | 返回档案：名字、阵营、等级、声望、联赛段位、版本、结局、总体统计、成就、技能与武器熟练度、赛季修正与进度、收藏物品、已装备物品（含配件 `children`）；竞技场有自己的字段（`arenaStats`、`battlePasses`） |
| 匹配时间 | `GET /atlas/api/matching?hours=<1–168>` | 公开，不需要密钥 |

- 模式 `mode` 取 `season`（默认）、`pvp`、`pve`、`arena`，与本插件的四个模式一一对应。接口主机统一用 `https://eftforge.com`（无 `www`）。本插件**总是显式带上 `mode`**，不依赖服务端默认值：插件自己的默认模式（`default_mode`）和“没有档案时换成有档案的模式”的逻辑照旧，只是每个模式各发一次请求。
- 输入校验：昵称 `^[A-Za-z0-9_.-]{3,15}$`，账号 ID 为 1～12 位数字。**昵称最长 15 个字符**（本插件现在接受 3～24 个，系统生成的 `TarkovCitizen…` 名字最长 21 个，用 Atlas 昵称搜索会被拒绝，需要用账号 ID）。
- 响应头 `Cache-Control: no-store`（玩家查询）；匹配时间为 `public, max-age=60`。

### 2.3 密钥

- **查询和匹配时间不需要密钥**（作者确认）。因此第一阶段的客户端不带密钥，也不需要在配置里填密钥。
- 公开代码里密钥的写法是请求头 `X-Atlas-Key: atl_…` 或 `Authorization: Bearer atl_…`；密钥有作用域 `changes`（变更集）和 `lookup`（玩家查询），带密钥时限额改按密钥计。错误或已吊销的密钥直接 403（同一 IP 失败 5 次锁定 10 分钟），不会降级为公开限额。这些只作参考：除非 Atlas 开发者说明刷新要带密钥，否则插件**不发送密钥**。
- 刷新密钥的用途、作用域和写法，等 Atlas 开发者回答（2.6）。拿到后密钥只能在服务器端使用（Atlas 不开放 CORS），不进仓库、日志和聊天。

### 2.4 限额与并发

不带密钥（本插件的默认方式）：

| 项 | 数值 |
|---|---|
| 来源 IP | 每分钟 20 次、每小时 200 次（作者确认，与代码一致）。**按机器人服务器的出口 IP 计，所有用户共用一份额度** |
| 超出限额 | 429 `{"error":"rate","retryAfter":秒}`，带 `Retry-After`；被拒绝的请求不计数，等过窗口即可 |
| 搜索和查询 | 各算一次：按昵称查一名没记录过的玩家要 2 次，按账号 ID 或已记录的昵称只要 1 次 |
| 并发 | 全站同时最多 8 个查询，与网站访客共用；超出立刻返回 429 `busy`（`Retry-After: 5`），**不计入限额** |
| 缓存 | 服务端对同一查询缓存 60 秒，命中时响应里带 `"cached": true`，不消耗限额 |
| 超时 | 上游自己控制节奏，一次查询可能等几秒；转发层超时 30 秒 |
| nginx | 前面还有一层每 IP 每分钟 60 次的限制 |

参考（带密钥时，公开代码里的数值，本插件暂不使用）：每个密钥每分钟 40 次、每小时 1200 次，带密钥的请求合计最多占 3 个并发。

错误码：`session`、`backend`、`not_found`、`no_profile`、`mode`、`bad_account`、`bad_nickname`、`rate`、`busy`；未知错误统一为 `lookup`；服务未配置为 503 `unavailable`；上游连不上为 502。

### 2.5 匹配时间的返回

`server_time`、`updated`（最近一次采样时间）、`hours`、`datacenters:[{region, name, wait}]`（`wait` 为整数秒或 `null`）、`history:{start, step, series:{数据中心名:[秒或 null,…]}}`。采样约每 100 秒一次，历史最多 288 个点，范围 1～168 小时。公开、不需要密钥；服务端自己缓存 60 秒（`Cache-Control: public, max-age=60`），作者要求客户端也缓存、不高频轮询。**这个接口没有模式参数**（网页上的模式切换对匹配时间不起作用，至少代码里是这样）。

### 2.6 没查明的：“刷新”

公开代码中没有任何刷新玩家数据的参数、路径或密钥作用域；转发层只有 60 秒的结果缓存。所以“主动刷新”依赖 Atlas 开发者提供的、尚未公开的接口。**实现前必须向 Atlas 开发者问清：**

1. 刷新的请求方式（新路径？`lookup` 加参数？）、刷新密钥怎么用（请求头？哪个作用域？）；
2. 刷新是同步还是异步（返回新数据，还是只返回“已受理”）；
3. 刷新是否计入每 IP 每分钟 20 次、每小时 200 次的限额，有没有单独的限额或冷却，同一玩家有没有最短刷新间隔；
4. 响应里怎样表示数据的更新时间（用于“数据是几分钟前的”提示）；
5. 刷新对四个模式是否都有效；
6. 请求头里的 `User-Agent`、署名或联系方式有没有要求；
7. 接口地址用哪个域名（`eftforge.com` 还是 `www.eftforge.com`），以及接口稳定性/改动通知的方式。

### 2.7 其他规范和礼仪

- Atlas 写明自己“放在 eftforge.com 只是为了降低托管成本”，是个人维护的服务：**不做后台轮询、不预取、不批量遍历账号**，只在用户发命令时请求；尊重上面的限额和缓存。
- 许可：EFTForge 是 AGPL-3.0-or-later，附加条款（第 7(b) 条）要求“传播或基于该程序的作品”保留署名“Based on EFTForge by Morph1ne”并链接仓库。本插件只调用其接口，不包含它的代码，严格说不在这个条款范围内；仍然在 README 特别致谢里写明名称和链接。**不抄它的代码和图片**（它的图片是游戏素材，另有来源说明）。
- Atlas 自称是粉丝项目，与 Battlestate Games 无关；本插件的声明保持一致。

## 3. 玩家查询重做（方案）

### 3.1 数据流

- 按昵称：`search`（带 `mode`）得到候选（账号 ID + 昵称）→ 再 `lookup`（带 `mode`）。昵称与账号 ID 的对应继续写进现有 `accounts.names`。
- 按账号 ID 或玩家页网址：直接 `lookup`。
- **模式与额度**：现在的插件每次查询同时拉 PVP、PVE、赛季三个模式（档案是快照，读取便宜）；Atlas 每个模式都是单独一次请求，照搬会让每次查询花 3 次额度，每小时 200 次只够约 66 次查询。方案：**只请求用户指定的模式，没指定时只请求 `default_mode`**，一次查询 1 次请求；“其他模式也有档案”的提示改为用户主动发 `tarkov 全部 <目标>` 之类的命令才逐个模式查（每个模式 1 次，受冷却和预算限制），或者在 `player_source` 为快照时保留现状。待维护者决定（5.9）。
- 绑定：沿用现有 `accounts.bindings`（带密钥的哈希），不变。
- 与现状的关系：现在是“读 tarkov.dev 的快照，玩家要先在网站搜索过”；Atlas 的上游据称可以按昵称或账号 ID 查询任何玩家，**第一次查询前先去网站搜索一次这条限制很可能消失**（待 Atlas 开发者和实测确认）。

### 3.2 刷新

- 新增命令，例如 `tarkov 刷新 [模式] [目标]`（QQ 单词命令 `trefresh`，名称待定）；不带目标时刷新自己绑定的账号。
- 回复里显示“数据时间”，并说明是缓存还是刚刷新的。
- 防滥用（Atlas 的额度按机器人的出口 IP 计，所有用户共用）：刷新单独设置权限（默认仅管理员，可改为所有人）、每人冷却、全局每分钟预算；预算用尽时回复“稍后再试”，不报“没有这名玩家”。

### 3.3 数据来源切换

- 设置 `player_source`：`atlas`（默认）/ `tarkov-dev`（现有快照）。Atlas 出错或不可用时是否自动回退到快照，待决定（5.2）。
- 现有 tarkov.dev 代码路径保留，不删除。

### 3.4 内容映射

- 第一阶段：把 Atlas 档案映射到现有卡片（等级、阵营、PMC/Scav 战局、存活率、K/D、技能、竞技场段位与 ARP），保持图片/文字/Markdown 三种输出不变。
- 暂不做：装备、收藏物品、武器图（Atlas 的武器图是它自己绘制的，通过另一个图片地址提供；接入要新增图片下载路径，另行决定）。
- 需要用真实响应样本确认字段后再定映射；样本只存在开发环境里，不进仓库（仓库里只用虚构数据）。

### 3.5 本地限流与缓存（额度很紧，是这个方案最大的约束）

Atlas 按 IP 每小时只给 200 次，机器人所有用户共用。按昵称查一名新玩家要 2 次，所以一小时大约只够 100 次“新昵称”查询。对策：

- **本地预算**：每分钟不超过 15 次、每小时不超过 150 次（留出余量，给刷新和网络抖动）；预算用完时回复“查询太频繁，约 N 分钟后再试”，不是“没有这名玩家”。设置里可调，但上限不超过 Atlas 的限额。
- **用户冷却**：每人两次查询之间的最短间隔（默认 10 秒，可调）；刷新另有更长的冷却（默认 5 分钟，可调）。已有的“每人同时一个查询”和相同请求合并保留。
- **缓存**：本地缓存不短于 Atlas 的 60 秒；现有 `profile_cache_minutes`（默认 10 分钟）继续沿用，命中时不请求 Atlas。刷新绕过缓存，但仍受冷却和预算约束。
- **少用搜索**：昵称与账号 ID 的对应继续记进 `accounts.names`，已记录的昵称直接 `lookup`（1 次）；绑定后查自己也是 1 次。
- **429**：`rate` 按 `Retry-After` 暂停整个 Atlas 客户端（不是只暂停这一个用户）；`busy` 等 `Retry-After`（默认 5 秒）后最多重试一次。不在后台重试，不排队。
- 并发不超过 2 个；`cached: true` 时如实标注。
- 多个机器人共用同一出口 IP（例如同一台服务器上的其他实例）会分摊这份额度，部署文档里要提醒。

## 4. 服务器匹配时间（方案）

- 命令：`tarkov 匹配 [小时数]`（别名 `matching`，QQ 单词命令 `tmatch`，名称待定）；默认 24 小时，范围 1～168。
- 输出：图片（默认）、文字、Markdown 三种**一开始就都做**（遵照维护者 2026-10-24 的要求，不重复状态/Boss 只有图片的缺口）。图片：每个数据中心当前等待时间 + 所选范围的折线；顶部写更新时间。数据中心名称和地区原样显示，是否加中文名待看真实数据。
- 数据为 `null` 时写“暂无数据”，**请求失败不等于等待时间为 0**，也不等于服务器宕机。
- 公开接口，不需要密钥（作者确认），因此可以最先实现，也是验证 Atlas 接入、网络和图片管线的最小切入点。
- 只在用户发命令时请求，**不做后台轮询**（作者要求）；本地缓存默认 2 分钟（设置里可调，最短 60 秒，与 Atlas 的服务端缓存一致）。同一时间多人查询共用一次请求。遇到 429 按 `Retry-After` 等待。是否做“匹配时间变化推送”不在本次范围，做的话需要单独评估请求频率。
- 接口主机：作者给的是 `https://eftforge.com/atlas/api/matching`（无 `www`）。

## 5. 需要维护者决定的事

1. **优先顺序**（建议：先做匹配时间，再做玩家查询）。理由：匹配时间公开、无密钥、不依赖未公开的刷新接口，可以先把客户端、网络、图片管线跑通。缺点：用户最关心的玩家查询要晚一些。
2. **Atlas 出错或额度用尽时，是否回退到 tarkov.dev 快照**。回退：可用性高，也能缓解每小时 200 次的额度压力，但同一回复里数据口径不同，需要注明来源；不回退：口径一致，Atlas 不可用时玩家查询整体不可用。建议：回退，并在回复里写明“来自 tarkov.dev 快照”。
3. **谁能刷新**：默认仅管理员，还是所有人加冷却。额度这么紧，建议默认仅管理员，可在设置里改。
4. **本地预算和冷却的默认值**：建议每分钟 15 次、每小时 150 次，查询冷却 10 秒、刷新冷却 5 分钟（3.5）。
5. **命令名**：`刷新`/`refresh`、`匹配`/`matching` 以及 QQ 单词命令名是否合适。
6. **版本号**：建议新功能作为 0.5.0，而不是 0.4.x。
7. **向 Atlas 开发者确认 2.6 的七个问题**，其中最关键的是刷新接口和刷新密钥的用法；由谁去问。问清之前不写刷新的实现。
8. **本开发环境的网络**：实测需要允许访问 `eftforge.com`（作者给的主机，无 `www`）；本环境的代理目前拦截它。我会在你同意后再提交环境修改申请。刷新密钥拿到后只通过安全表单保存，不在聊天里粘贴。
9. **多模式策略**：Atlas 下是否只查一个模式（建议，省额度），放弃“三个模式一起看”和“默认模式没有档案时自动换模式”；还是仍然三个模式一起查（体验与现在一致，但额度只够约 66 次查询/小时）。

### 6.2 要同步修改的不变量（handoff §8）

- 允许的固定主机新增 Atlas 的接口主机（只此一个，不接受配置或接口返回的主机）。
- 密钥永不进日志、错误信息、聊天消息、测试夹具、示例图和数据库；异常只显示类型名；`__repr__`/调试输出不含密钥。
- 不用 Atlas 做后台轮询或批量查询；不绕过它的限额，不伪造来源。

### 6.3 设置（草案）

新增一组 `atlas`：`player_source`、`refresh_permission`、`refresh_cooldown_seconds`、`lookup_cooldown_seconds`、`atlas_budget_per_minute`、`atlas_budget_per_hour`、`matching_enabled`、`matching_cache_seconds`。查询和匹配时间不需要密钥，所以现在没有密钥设置；刷新密钥确认用法后再加一项 `atlas_refresh_key`（AstrBot 配置里是明文，README 要提醒像对待密码一样保管配置目录）。主机地址不做成设置。

### 6.4 测试与验证

- 单元测试：请求头、各错误码与 `Retry-After`、`busy` 不计限额、令牌桶、并发上限、`cached` 标注、昵称长度、密钥不出现在任何输出里（含异常与日志）。
- 契约测试：用虚构样本（结构照 2.4/2.5，不含真实玩家）。
- 只读实测：匹配时间（公开）；玩家查询只用维护者同意的账号，样本不入库。
- 本环境网络：`eftforge.com` 目前被代理拦截（CONNECT 403），实测前需要放行。
- QQ/聊天平台的实际收发仍需在机器人端验收。

## 7. 风险

- **依赖私有上游和单人维护的服务**：接口可能变、限额可能调、密钥可能被吊销。对策：契约测试、错误码映射、回退到 tarkov.dev、对 Atlas 开发者留联系渠道。
- **共用 IP 的额度**：机器人所有用户共用每分钟 20 次、每小时 200 次；群里多人同时查询、或同一 IP 上有多个实例都会触顶。对策：本地预算与冷却、缓存、少用搜索、刷新权限、回退到 tarkov.dev 快照。
- **刷新接口未知**：可能与假设不符（异步、单独限额等），因此 P4 要等 Atlas 开发者的说明。
- **数据口径变化**：Atlas 档案字段与 tarkov.dev 快照不同（例如 K/D、游戏时长的算法），迁移后部分数字可能与以前的回复不一致，需在文档里说明。
