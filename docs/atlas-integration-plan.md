# Atlas 接入规划：可主动刷新的玩家查询与服务器匹配时间

当前限流规则（维护者修订，2026-11-08）：共用间隔最低 10 秒；每人每小时查询固定 10 次、刷新固定 3 次，不再提供次数设置；个人查询间隔最低 30 秒，刷新间隔最低 300 秒；本插件玩家请求每分钟上限最多 10 次。总额度用完时进入可恢复冷却，保留缓存读取，到期后由下一次查询恢复，不再因为本地总额度耗尽回退快照。下文旧的默认值和可配置次数保留为历史规划，以本段及玩家查询文档为准。

日期：2026-11-08。状态：**匹配时间已在 0.5.0 发布（只有图片，见 [matching.md](matching.md)）；Atlas 玩家查询已接入 PVP、PVE、赛季和竞技场。竞技场采用已确认的选手名册、分区汇总表和前 9 项稀有成就，进度与验证见 handoff 的“Atlas Arena register”一节。** 2.5 的问题已由第二轮实测回答（[atlas-probe-record.md](atlas-probe-record.md) 第 7 节）：数据时间是 `looked_up`，刷新就是再查一次，四个模式都有效。本稿保留原方案和实测记录。

**维护者决定（2026-11-08）**：先做匹配时间，再做玩家查询；查询必须声明模式，没写时默认查 PVE；先查 tarkov.dev 的昵称/ID 名单，再调用 Atlas；刷新做在查询里，配合用户查询限额；Atlas 出错或额度用尽时回退到 tarkov.dev 快照；本次只涉及免密钥调用。

## 本轮后端规划补充（2026-11-08）

维护者要求先规划“服务器匹配时间后端 + Atlas 匹配时间/玩家查询共用的全局冷却”。详细范围、请求准入语义、建议默认值和验收见 [atlas-matching-backend-plan.md](atlas-matching-backend-plan.md)。本轮不实现玩家查询或聊天输出；匹配时间后端不再依赖 P1 玩家响应实测，本文 §6.1 的 P1 → P2 → P3 顺序不适用于这次独立后端工作。共享冷却也不代替后续玩家分钟/小时预算。现已按维护者后续指示完成后端、配置、生命周期和测试，详细进度见细化规划 §9；聊天命令与输出层尚未接入。维护者随后明确：匹配时间由全部用户和群聊共用一份结果，独立冷却/缓存时间 15 分钟，期间查询读取缓存；失败最多回退到获取后 60 分钟内的旧结果，冷却期间按缓存输出，无可用结果时才报告查询失败。以下旧草案中匹配缓存 2 分钟、可变小时数等建议以本轮细化规划为准。

## 1. 目标与作者的说明

1. 用 [Atlas](https://www.eftforge.com/atlas) 的接口重做玩家数据查询，并支持主动刷新。
2. 新增服务器匹配时间查询（各数据中心的平均匹配等待时间）。
3. 在 README 的“特别致谢”里写明 Atlas（已完成）。

**Atlas 作者的说明（2026-11-08，优先于下文对公开代码的推断）：**

- 匹配时间接口 `https://eftforge.com/atlas/api/matching` 是公开的，可以直接使用；要求**做缓存，不要高频轮询**。
- **匹配时间和玩家查询都不需要密钥**，直接调用即可。本次规划与开发不涉及密钥。
- 玩家查询按 IP 限流：**每分钟 20 次、每小时 200 次**。刷新**计入**这个限额；刷新没有单独的限额和冷却，**需要我们自己做限制**。
- 可以在插件里做缓存和用户冷却；遇到 429 **按 `Retry-After` 等待**。
- 请求头（`User-Agent`、署名、联系方式）**无要求**。
- **玩家查询的流程**：先 `https://eftforge.com/atlas/api/lookup/search?nickname=<昵称>` 搜索，再用 `https://eftforge.com/atlas/api/lookup?accountId=<账号ID>` 查询详情；两个接口都可以加 `mode` 参数（`season`、`pvp`、`pve`、`arena`），**不写时默认是 `season`**。
- **账号 ID 与 tarkov.dev 通用**：Atlas 用的就是游戏后端响应里的账号 ID，同一个账号在各个模式下 ID 相同，查询时用 `mode` 选择模式。所以可以先用 tarkov.dev 的昵称/ID 对照得到账号 ID，只调用 `lookup`，**请求减少一半**；如果查到的昵称和 Atlas 返回的不一致，或对照表里找不到，再用 `lookup/search` 搜索。
- 搜索和查询返回 `busy`（429，`Retry-After: 5`）：作者说明是**网站服务器端的 8 个同步查询位置都满了**。这些位置与网站访客共用，满了就立刻拒绝，不是我们超限，也不计入每 IP 的额度。
- 刷新响应里怎样表示数据更新时间、刷新对四个模式是否都有效：作者让我们**实际请求后分析**（见 2.5、2.7）。

## 2. 已查明的使用规范

### 2.1 证据来源和可信度

- 来源：作者的上述说明；EFTForge 公开仓库（`SouthHorizons76/EFTForge`，提交 `ca6da4b`，2026-11-08）里网页后端的转发层（`backend/routers/atlas.py`、`atlas_lookup.py`、`services/lookup_guard.py`）和前端；本开发环境对线上服务的只读实测（2.7）。
- 仓库里**有**网页后端，但只是“转发层”；玩家数据由一个私有的上游提供方回答，那部分的实现不在仓库里。下面写的是对外接口的约定，不是上游的内部行为。
- 接口随时可能变。作者的说明和实测优先于代码阅读。

### 2.2 接口

| 用途 | 请求 | 说明 |
|---|---|---|
| 按昵称找人 | `GET /atlas/api/lookup/search?nickname=<名>&mode=<模式>` | 返回 `{nickname, players:[{accountId, nickname}]}` |
| 查一名玩家 | `GET /atlas/api/lookup?accountId=<数字>&mode=<模式>` | 返回档案：名字、阵营、等级、声望、联赛段位、版本、结局、总体统计、成就、技能与武器熟练度、赛季修正与进度、收藏物品、已装备物品（含配件 `children`）；竞技场有自己的字段（`arenaStats`、`battlePasses`） |
| 匹配时间 | `GET /atlas/api/matching?hours=<1–168>` | 公开；**没有模式参数** |

- 模式 `mode` 取 `season`（默认）、`pvp`、`pve`、`arena`，与本插件的四个模式一一对应。**插件总是显式带上 `mode`**，不依赖服务端默认值。
- **接口主机用 `https://www.eftforge.com`**：实测 `https://eftforge.com` 会 301 跳转到 `www.eftforge.com`，插件不跟随跳转，所以必须直接用 `www`。
- 输入校验：昵称 `^[A-Za-z0-9_.-]{3,15}$`，账号 ID 为 1～12 位数字。**昵称最长 15 个字符**（本插件现在接受 3～24 个，系统生成的 `TarkovCitizen…` 名字最长 21 个，不能用 Atlas 搜索，只能通过 tarkov.dev 名单或账号 ID）。
- 响应头：玩家查询 `Cache-Control: no-store`；匹配时间 `public, max-age=60`。

### 2.3 限额、并发与错误

| 项 | 数值 |
|---|---|
| 来源 IP | 每分钟 20 次、每小时 200 次（作者确认）。**按机器人服务器的出口 IP 计，所有用户共用一份额度**；刷新也计入 |
| 超出限额 | 429 `{"error":"rate","retryAfter":秒}`，带 `Retry-After`；被拒绝的请求不计数，等过窗口即可 |
| 搜索和查询 | 各算一次：按昵称查一名没记录过的玩家要 2 次，已知账号 ID 只要 1 次 |
| 并发 | 全站同时最多 8 个同步查询位置（作者确认），与网站访客共用；位置全满时立刻返回 429 `busy`（`Retry-After: 5`），**不计入限额**。2026-11-08 实测时多次遇到，说明高峰期不会很少见 |
| 缓存 | 服务端对同一查询缓存 60 秒，命中时响应里带 `"cached": true`，不消耗限额 |
| 超时 | 上游自己控制节奏，一次查询可能等几秒；转发层超时 30 秒 |
| nginx | 前面还有一层每 IP 每分钟 60 次的限制 |

> **待更新（2026-11-10，维护者）**：上游已放宽接口的使用速率限制，上表的数值是 2026-11-08 的记录，已经过时。放宽后的具体数值尚未写入本文档。插件的本地限额（3.5 及设置里的每分钟／每小时额度、每人次数和各项间隔）暂时保持不变，留待后续统一规划，见第 5 节“待定”第 6 项。

错误码：`session`、`backend`、`not_found`、`no_profile`、`mode`、`bad_account`、`bad_nickname`、`rate`、`busy`；未知错误统一为 `lookup`；服务未配置为 503 `unavailable`；上游连不上为 502。

### 2.4 匹配时间的返回

`server_time`、`updated`（最近一次采样时间）、`hours`、`datacenters:[{region, name, wait}]`（`wait` 为整数秒或 `null`）、`history:{start, step, series:{数据中心名:[秒或 null,…]}}`。采样约每 100 秒一次，历史最多 288 个点，范围 1～168 小时。服务端缓存 60 秒；作者要求客户端也缓存、不高频轮询。

### 2.5 刷新（待实测）

公开代码里没有刷新玩家数据的参数或路径，转发层只有 60 秒的结果缓存。作者确认的只有：刷新计入每 IP 的限额，限制要我们自己做；更新时间字段和各模式是否都能刷新要靠请求分析。

需要通过实际请求弄清（结果写进 2.7）：

1. 响应里哪个字段表示数据的更新时间（档案时间、抓取时间、`cached` 标记等）；
2. “刷新”在请求层面是什么：是否就是绕过缓存的再次 `lookup`（服务端缓存 60 秒，之后每次 `lookup` 是否都会重新向游戏后端取数），还是需要额外参数；
3. 四个模式（season、pvp、pve、arena）对同一账号是否都有数据、更新时间是否各自独立；
4. 同一账号连续请求时数据时间是否变化，变化的最短间隔。

### 2.6 其他规范和礼仪

- Atlas 写明自己“放在 eftforge.com 只是为了降低托管成本”，是个人维护的服务：**不做后台轮询、不预取、不批量遍历账号**，只在用户发命令时请求；尊重上面的限额和缓存；429 按 `Retry-After` 等待。
- 许可：EFTForge 是 AGPL-3.0-or-later，附加条款（第 7(b) 条）要求“传播或基于该程序的作品”保留署名“Based on EFTForge by Morph1ne”并链接仓库。本插件只调用其接口，不包含它的代码，严格说不在这个条款范围内；仍然在 README 特别致谢里写明名称和链接。**不抄它的代码和图片**（它的图片是游戏素材，另有来源说明）。
- Atlas 自称是粉丝项目，与 Battlestate Games 无关；本插件的声明保持一致。

### 2.7 只读实测记录（2026-11-08，本开发环境）

环境已放行 `eftforge.com`、`www.eftforge.com`、`players.tarkov.dev`。请求都带说明身份的 `User-Agent`，全部只读；样本只存在临时目录，不进仓库。完整的请求与返回见 [atlas-probe-record.md](atlas-probe-record.md)（玩家昵称和账号 ID 已打码）。

- **匹配时间**：`GET https://www.eftforge.com/atlas/api/matching?hours=1` → 200，gzip，`application/json`，`Cache-Control: public, max-age=60`。结构与 2.4 一致：28 个数据中心，`region` 为 RUS/EUR/USA/OCE/ASI/SAM/ME/AF；名称是英文（如 `Russia Central`、`Asia Central`）；个别名称带多余空格或前缀（如 `Sa   Colombia`、`Me   Dubai`、`Af Nigeria`），显示前需要规整；个别数据中心的 `wait` 为 `null`（`Europe South`）；`hours=1` 时历史步长 300 秒、每个数据中心 12 个点。数值是几十到几百秒不等。
- **主机**：`https://eftforge.com/...` 返回 301 到 `https://www.eftforge.com/...`。
- **玩家搜索与查询**：从 tarkov.dev 的 PVE 昵称名单（138,465 个，其中 31 个昵称超过 15 个字符）取随机账号做 `lookup/search` 和 `lookup`，最初几次都返回 429 `{"detail":{"error":"busy"}}`，`Retry-After: 5`（作者说明 Atlas 那边是正常的）；之后改为严格按 `Retry-After`（5 秒起，逐次加倍）等待再试 5 次：**全部仍是 `busy`**。作者回复原因是网站服务器端的 8 个同步查询位置都满了。到目前为止**没有拿到任何一份成功的 `lookup` 响应**，所以 2.5 里的更新时间字段、刷新含义、四个模式是否有效**还没有结论**。已停止请求，等位置空闲时再试，或请作者提供一份样例响应。
- tarkov.dev 的名单可正常下载（PVE，1.5 MB gzip）。

## 3. 玩家查询重做（方案）

### 3.1 数据流

- **模式必须声明，默认 PVE**（维护者决定）：Atlas 下**每次查询只请求一个模式**，一次 1 次请求；没写模式时查 PVE（`default_mode` 的默认值相应设为 `pve`，仍可在设置里改）。取消“同时拉三个模式”和“默认模式没有档案时自动换模式”。想看别的模式，用户明确写出模式再查。账号 ID 在各模式下相同，所以换模式不需要重新解析昵称。
- **昵称解析顺序**（账号 ID 与 tarkov.dev 通用，作者已确认）：
  1. 本插件已记录的昵称（`accounts.names`）；
  2. tarkov.dev 的昵称名单（`name_index_enabled` 已有的本地数据库，按所选模式）→ 得到账号 ID → 直接 `lookup`（1 次请求）；
  3. 对照表里找不到，或 `lookup` 返回的昵称与用户输入不一致（改过名、名单过期）→ 用 Atlas 的 `lookup/search` 搜索，再 `lookup`（2 次请求）。
- 按账号 ID 或玩家页网址：直接 `lookup`。
- 昵称与账号 ID 的对应继续写进现有 `accounts.names`；绑定沿用现有 `accounts.bindings`（带密钥的哈希，与 Atlas 无关），不变。
- 昵称超过 15 个字符的（系统生成名）只能走第 1、2 步或账号 ID。
- 与现状的关系：现在是“读 tarkov.dev 的快照，玩家要先在网站搜索过”；Atlas 可以按昵称或账号 ID 查询，第一次查询前先去网站搜索一次这条限制很可能消失（待实测确认）。

### 3.2 刷新（做在查询里，配合用户限额）

- 维护者决定：**不做独立的刷新命令，而是在查询时刷新**，并建立用户查询限额机制。
- 草案：查询命令可以带一个“刷新”标记（写法待定，例如 `tarkov pve 昵称 刷新`）；带标记时绕过本地缓存，向 Atlas 重新请求，不带时用缓存（命中则不请求 Atlas）。
- 用户限额：每人每小时可查询 N 次、其中可刷新 M 次（建议查询 20、刷新 3，设置里可调）；超出时提示“已达上限，约 N 分钟后再试”，不影响别人。另有全局预算（3.5），预算耗尽时刷新先被拒绝、普通查询继续用缓存或回退。
- 回复里显示“数据时间”，并说明是缓存还是刚刷新的。数据时间用哪个字段，取决于 2.5 的分析。
- Atlas 对刷新没有单独限额，刷新与普通查询一样计入每 IP 的额度，所以限制全部由插件承担。

### 3.3 数据来源切换

- 设置 `player_source`：`atlas`（默认）/ `tarkov-dev`（现有快照）。Atlas 出错、额度用尽或被限流时**回退到 tarkov.dev 快照**（维护者决定），回复里注明“来自 tarkov.dev 快照”和快照时间。
- 现有 tarkov.dev 代码路径保留，不删除。

### 3.4 内容映射

- 第一阶段：把 Atlas 档案映射到现有卡片（等级、阵营、PMC/Scav 战局、存活率、K/D、技能、竞技场段位与 ARP），保持图片/文字/Markdown 三种输出不变。
- 暂不做：装备、收藏物品、武器图（Atlas 的武器图是它自己绘制的，通过另一个图片地址提供；接入要新增图片下载路径，另行决定）。
- 需要用真实响应样本确认字段后再定映射；样本只存在开发环境里，不进仓库（仓库里只用虚构数据）。

### 3.5 本地限流与缓存（额度很紧，是这个方案最大的约束）

Atlas 按 IP 每小时只给 200 次，机器人所有用户共用。有了 tarkov.dev 名单，大部分查询只要 1 次请求，只有对照表里找不到或昵称不一致时才要 2 次。对策：

- **本地预算**：每分钟不超过 15 次、每小时不超过 150 次（留出余量，给刷新和网络抖动）；预算用完时回复“查询太频繁，约 N 分钟后再试”，不是“没有这名玩家”。设置里可调，但上限不超过 Atlas 的限额。
- **用户冷却**：每人两次查询之间的最短间隔（默认 10 秒，可调）；刷新另有更长的冷却（默认 5 分钟，可调）。已有的“每人同时一个查询”和相同请求合并保留。
- **缓存**：本地缓存不短于 Atlas 的 60 秒；现有 `profile_cache_minutes`（默认 10 分钟）继续沿用，命中时不请求 Atlas。刷新绕过缓存，但仍受冷却和预算约束。
- **少用搜索**：见 3.1 的解析顺序。
- **429**：`rate` 按 `Retry-After` 暂停整个 Atlas 客户端（不是只暂停这一个用户）；`busy` 等 `Retry-After`（默认 5 秒）后最多重试一次，仍然 `busy` 就按 3.3 回退到 tarkov.dev 快照（回复里注明），不在后台重试，不排队。`busy` 不算失败，也不能说成“没有这名玩家”。
- 并发不超过 2 个；`cached: true` 时如实标注。
- 多个机器人共用同一出口 IP（例如同一台服务器上的其他实例）会分摊这份额度，部署文档里要提醒。

## 4. 服务器匹配时间（方案）

- 命令：`tarkov 匹配 [小时数]`（别名 `matching`，QQ 单词命令 `tmatch`，名称待定）；默认 24 小时，范围 1～168。
- 输出：图片（默认）、文字、Markdown 三种**一开始就都做**（遵照维护者 2026-10-24 的要求，不重复状态/Boss 只有图片的缺口）。图片：每个数据中心当前等待时间 + 所选范围的折线；顶部写更新时间。数据中心名称和地区原样显示（规整多余空格），是否加中文名待定。
- 数据为 `null` 时写“暂无数据”，**请求失败不等于等待时间为 0**，也不等于服务器宕机。
- 公开接口，不需要密钥，因此可以最先实现，也是验证 Atlas 接入、网络和图片管线的最小切入点。
- 只在用户发命令时请求，**不做后台轮询**（作者要求）；本地缓存默认 2 分钟（设置里可调，最短 60 秒，与 Atlas 的服务端缓存一致）。同一时间多人查询共用一次请求。遇到 429 按 `Retry-After` 等待。是否做“匹配时间变化推送”不在本次范围，做的话需要单独评估请求频率。
- 接口主机：直接请求 `https://www.eftforge.com/atlas/api/matching`（`eftforge.com` 会 301 到 `www`）。

## 7. 风险

- **依赖私有上游和单人维护的服务**：接口可能变、限额可能调。对策：契约测试、错误码映射、回退到 tarkov.dev。
- **共用 IP 的额度**：机器人所有用户共用每分钟 20 次、每小时 200 次；群里多人同时查询、或同一 IP 上有多个实例都会触顶。对策：名单优先减少请求、本地预算与冷却、缓存、用户限额、回退到 tarkov.dev 快照。
- **刷新的含义未定**：可能就是绕过缓存的再次查询，也可能需要额外参数，因此 P4 要等实测分析。
- **数据口径变化**：Atlas 档案字段与 tarkov.dev 快照不同（例如 K/D、游戏时长的算法），迁移后部分数字可能与以前的回复不一致，需在文档里说明。
