## 1. 交付目标与范围

本轮实施目标是让现有匿名玩家查询、改名核验、夜间统计和错误处理适应 rev7：

1. 夜间统计请求明确发送 `art=0`。
2. 资料昵称与查询昵称不一致时，用 `live=1` 核验。
3. 收到403后暂停相关请求，管理员处理后明确恢复。
4. 昵称问题继续核实与规划，本轮不增加前缀拦截或点号兼容。
5. 更新上游额度说明，保持已有本地预算和个人限制。
6. 将 JSON 缓存、原始历史和数字样本的规则边界确认清楚，再执行相应存储变更。

本轮继续使用匿名调用。上游额度不在项目文档重复列出；本地默认每分钟15次、每小时200次，分钟可设1～15、小时可设1～200；已有更低配置不自动改写；个人每小时10次查询/3次刷新及30秒/300秒间隔保持现有规则。共享间隔、夜间03:00～09:00（UTC+8）、140～180秒采样间隔、匹配缓存与默认来源保持现状。

实施分为两部分：第一部分处理已明确的调用与输入问题；第二部分处理依赖提供方答复的缓存/历史政策。第二部分未决时，第一部分仍可形成独立可审阅的修复。

## 4. T02：统计请求禁绘图与缓存隔离

### 4.1 接口和参数

建议使用以下内部接口，新增参数均为仅限关键字的布尔值：

```python
AtlasClient.lookup(account_id, mode, *, include_art=True, max_wait=None, deadline=None)
AtlasPlayers.profile(mode, aid, *, refresh=False, charge=..., include_art=True)
AtlasPlayers.profile_once(mode, aid, *, deadline=None, include_art=False)
AtlasPlayers._fetch(mode, aid, *, retry=True, deadline=None, include_art=True)
```

- include_art=True沿用原请求，不额外发送art参数；False仅生成`art=0`。
- 拒绝字符串、数字等伪布尔参数；HTTP白名单仅接受accountId、mode，以及可选且值必须为`0`的art。
- `main.py::weekly_fetch`明确传False，不依赖未来默认值。deadline和单次后台请求语义原样传递。
- `render`或`character`为null是正常统计响应；样本只读数字字段，不补发绘图请求。

### 4.2 缓存与任务隔离

采用明确的变体键：`(mode, account_id, include_art)`。缓存、负结果和前台pending表统一使用此键，总容量仍为现有256项缓存/32个pending上限，不按变体各开一份容量。

后台`profile_once`仍不加入前台shielded任务；取消后台不得取消用户查询。统计响应只能更新自己的变体，不能替换完整资料；本阶段不增加跨变体推断或额外请求优化。

### 4.3 原始历史的兼容迁移

现有历史唯一键是`(account_id, mode, looked_up)`。若直接让无图响应先入库，同时间戳的完整响应会被INSERT OR IGNORE丢弃。计划采用增量迁移：

1. 检查`PRAGMA table_info(lookups)`；无字段时事务内添加`include_art INTEGER NOT NULL DEFAULT 1`，旧记录按旧版请求变体解释为1，不推断其实际上有没有图片。
2. 同唯一键不存在时正常插入，记录请求变体；已存在时仅允许由0升级为1，更新相应body、size和获取时间，再执行现有容量清理。
3. 1不被0覆盖；相同变体重复仍不新增，账号、模式和looked_up不改。升级不建立第二份完整数据库，不删除已有行。
4. 读取接口保留既有字段，按需要附加变体元数据；统计提取和周报数字库不依赖图片字段。

此迁移解决文档完整度，不能替代T06的政策答复。如果上游要求停止原始历史，改为执行T06的停写方案，不为此继续扩建原始归档。

完成标准：夜间HTTP带art=0；统计/完整资料并发、同时间戳和重启均不错误覆盖；没有新增HTTP；09:00截止仍覆盖排队和在途请求。

## 5. T03：改名核验强制live搜索

接口：`AtlasClient.search(..., live=False)`、`AtlasPlayers.search(..., live=False)`；后台`search_once`同样接受显式参数但保持默认False。live=True仅生成`live=1`，参数白名单拒绝其他值与未知参数。

保持`AtlasPlayers.search`现有候选列表返回形式。本轮不为source=index引入全新返回类型或上游计费优化；普通搜索继续允许索引结果。

执行流程：

1. 先按本地记录/名单解析ID并lookup。
2. 资料昵称与用户目标一致时结束；不同且可搜索时，至多进行一次`live=True`核验。
3. 重新严格匹配live候选。唯一候选为原ID：按新资料说明改名；唯一候选为其他ID：lookup确认该候选，确认后展示/绑定对应账号。
4. 无结果或多结果：查询回复说明旧记录对应的账号及“昵称未核实”，要求使用ID；绑定不以未核实昵称自动确认归属。
5. 核验超时、429或本地预算不足：不循环搜索，不换模式重试；保留已有请求的用户计数，给出明确核验失败提示。已有可信ID的普通资料可带说明展示。

完成标准：模拟旧索引A、资料已改名、live命中B时，实际请求包含live=1且展示/绑定到经确认的B；各失败分支不绑定错人。

## 6. T04：拒绝访问的暂停与恢复

### 6.1 状态与作用范围

当前仅为匿名接口实现两个范围：`players`（lookup/search及周报）和`matching`。不引入真实key配置；未来key权限与身份隔离另行设计。

已新增`atlas_access.py`，状态为：

| 当前状态 | 事件 | 后续状态与行为 |
|---|---|---|
| active | 收到403 | blocked；记录状态后阻止同范围后续HTTP |
| blocked | 用户查询/夜间采样/普通重载 | 维持blocked；不发送Atlas请求 |
| blocked | 管理员一次性恢复动作保存成功 | probe_ready；等待下一次正常需求，不立即启动联网 |
| probe_ready | 下一次合法请求获得共享准入 | probing；只允许一个探测请求 |
| probing | 收到200且传输/JSON校验通过 | active，恢复正常调用 |
| probing | 403/意外401/其他非200/连接失败/响应无法校验 | blocked；本轮探测结束，不自动再探测 |
| probing | 429或带Retry-After的5xx | blocked，并保留上游等待时间；管理员再次恢复也不得早于该等待时间发送 |
| probing | 进程结束或请求取消 | 保守恢复为blocked，不把未确认请求记为成功 |

匿名接口意外401也按访问配置问题暂停相关范围；以后新增需要key的接口时，401再对应缺失认证。429在正常active状态仍使用现有定时冷却，不变成需要人工恢复的普通限流。

### 6.2 准入、计数和并发

1. 在进入等待前检查访问状态；获得现有共享gate后、reserve预算前再检查，避免403前已排队的请求继续发送。
2. 拒绝状态在释放共享gate前更新内存并完成持久化尝试，保证当前进程后续调用可见。
3. 发送前被暂停拦截使用专门的`AtlasAccessPaused`异常，归入现有NOT_SENT语义；不扣全局预算，未发生其他已发送请求时才退还本次用户次数。
4. 实际收到403的请求已经发送，不能按NOT_SENT退还；第一次查询里的其他已发送请求也照常计数。
5. 已标明来源的tarkov.dev快照回退可继续，但不能声称Atlas已恢复。matching的403从原2分钟短窗口转为访问暂停；其他404等行为单独保留，不混成认证问题。

### 6.3 持久化与生命周期

- 使用插件数据目录的`atlas-access.json`，仅存版本、范围、状态、HTTP码和发生时间；不存账号、昵称、聊天消息、URL、原始错误正文或密钥。
- 原子临时文件替换，文件I/O放在线程；缺文件视为首次启动，损坏/不支持版本则阻止相关Atlas调用并提示修复，不静默清空。
- 首次发送前必须完成状态加载；`initialize`中在启动周报前加载，也为未初始化就被调用的客户端提供共享的惰性加载屏障。
- probe_ready可以跨重启保留；持久化probing在启动时转回blocked。当前进程若状态写入失败，保持内存暂停并报告错误；不能宣称写入失败后仍已保证跨重启保存。
- 不依靠修改全局冷却为无限等待实现暂停，避免players的拒绝误停matching及其他数据源。

### 6.4 管理员恢复与采样行为

已新增一次性设置`atlas_access_reset`，默认False，放在atlas组；开关含义写明“解除访问暂停，下一次正常查询仅探测一次”。沿用现有一次性动作：先复位并保存成功，再设置probe_ready；保存失败不解锁，不复制现有“保存失败仍继续动作”的路径。

恢复动作本身不访问网络，不清空用户额度、上游Retry-After或缓存；如果没有暂停则为空操作。普通保存、重载、改变代理或等待两分钟都不视为已修复权限。

周报暂停期间不逐人尝试：采样循环识别访问暂停，进入已有空闲等待并每次重查夜间窗口；不标记玩家无档案、不消耗其夜间失败次数。恢复后按原名单进度和140～180秒间隔继续，错过夜间不补跑。周报展示和已存样本查询保持可用。

完成标准：跨用户、模式及后台都无法绕过暂停；不同范围不误伤；重载不清除状态；恢复没有启动联网或突发补跑；探测只有一个，429等待不能被人工动作缩短。

## 7. T05：昵称问题的场景核实与后续方案（未执行）

### 7.1 原结论修正

原审查使用了人工构造的短字符串`TarkovCitizenAA`，只能证明客户端正则允许其进入搜索，不能证明真实系统生成昵称会采用这种格式，更不能证明正常查询会出错。常见的“前缀＋较长数字”已经超过15位，现有网络校验会拒绝。本项撤回“已证实生产bug”的定性。

| 场景 | 当前路径 | 是否已有bug证据 |
|---|---|---|
| 用户直接提供账号ID | 直接lookup，不进行昵称搜索 | 没有；无需修改 |
| 较长系统名，且本地已记录唯一ID | 本地解析后lookup | 没有；应保留 |
| 较长系统名，本地没有ID | 长度校验阻止Atlas搜索，提示使用ID | 没有；现有保护有效 |
| 人工输入13～15位同前缀字符串，本地无ID | 可能发送一次昵称搜索，交由上游回答 | 仅有人工边界复现，无真实生成名或错误结果证据 |
| 3～15位含点号昵称 | 入口拒绝，但Atlas客户端语法允许 | 已确认的兼容范围差异；旧测试有意固定，并非意外回归 |

### 7.2 核实步骤与交付物

1. 从提供方说明或维护者提供的脱敏样本确认系统生成名的合法格式、最短数字长度及用户是否可主动选择该前缀；不批量遍历玩家、不把真实名/ID写入仓库。
2. 先用本地样本重放“已知ID”“未知长名”“未知短前缀”三条路径；如需线上验证，只针对已明确授权的少量案例，保留脱敏结论。
3. 核实上游遇到不能搜索的昵称如何返回：明确错误、空候选还是unknown；检查现有代码是否误报、错误绑定、重复查询或实际绕过额度。
4. 交付场景表、脱敏契约样本和对用户的影响说明。没有实际失败时，维持现状，不为一条人工字符串增加业务分支。

### 7.3 可选择的实现范围

- **方案A，默认建议：维持前缀逻辑。** 保留现有长度校验和本地ID解析；如发现提示不清，只改准确文案。无需改索引数据或绑定。
- **方案B，有真实失败证据后增加保护。** 仅在即将发起Atlas昵称搜索前判断确认过的格式；已有唯一ID仍正常lookup，不能先在聊天入口统一拒绝全部同前缀名字。前台search、改名核验、后台search_once使用同一个函数。
- **点号兼容单独决定。** 如要扩展，只放开Atlas来源的入口；不自动截断、去点号或修改用户输入。同步QQ、绑定、帮助与现有刻意拒绝点号的测试；旧快照来源保留原规则。

### 7.4 验收和迁移

任何选定方案都必须证明：真实ID查询、已有长名映射、模糊候选、预算与绑定不回归；非法输入不会新增HTTP；不能把“不能搜索”解释为玩家不存在。本项没有数据库迁移，不删除或重写旧昵称记录。未取得必要证据前不将其列入修复交付。

## 8. T06：缓存与历史政策的决策分支

需要提供方明确的四个问题：插件内存TTL是否允许；原始JSON本地归档是否允许；周报数字样本是否允许；在途同请求合并是否属于限制范围。记录答复日期、适用接口及原文依据。本轮不代维护者联系提供方。

| 答复范围 | 执行办法 | 数据迁移 |
|---|---|---|
| 允许插件内部复用与归档，仅禁止中间层转发 | 保留TTL/历史选项，文档明确用途与保留期；继续T02完整度迁移 | 仅增加变体字段，不删记录 |
