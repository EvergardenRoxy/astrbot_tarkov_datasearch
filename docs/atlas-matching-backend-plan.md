# Atlas 匹配时间后端与共享查询冷却开发规划

日期：2026-11-08。状态：后端已实现并完成测试，聊天命令和输出层未接入。

维护者修正：匹配时间由全部用户和群聊共用一份结果，独立冷却（缓存有效期）15 分钟，期间额外查询均读取缓存；查询失败最多回退到获取后 60 分钟内的缓存。冷却期间按缓存正常输出，不报告剩余冷却时间；无可用结果时才报告失败。

本轮需求：实现服务器匹配时间查询的后端，并为 Atlas 匹配时间和未来的 Atlas 玩家查询提供全局共用的冷却。本文件先记录规划，现已按维护者后续“开始构建后端部分”的指示实施；当前实现进度见第 9 节。

本文细化并调整 [Atlas 总规划](atlas-integration-plan.md) 的本轮实施顺序；旧方案中的玩家接口实测不再作为匹配时间开发的前置条件。玩家刷新、映射和接入仍待后续开发。

## 1. 本轮交付边界

交付可以被插件命令层调用的匹配时间服务、Atlas 请求入口、共享冷却、配置接线、生命周期管理和自动测试。

- 按需访问 `GET https://www.eftforge.com/atlas/api/matching?hours=...`，不需要密钥。
- 校验并规范化当前等待时间与历史序列，返回结构化结果，附带数据时间、获取时间和缓存状态。
- 提供一个插件实例共用的 Atlas 请求控制器。未来玩家搜索、详情、刷新都必须复用它。
- 接入配置读取和插件关闭流程，但本轮不注册聊天命令、不添加帮助入口、不绘制图片、不实现文字/Markdown 排版。
- 不实现 Atlas 玩家搜索、详情、刷新、用户小时限额或全局分钟/小时预算；不改变现有玩家查询来源、默认模式和绑定行为。
- 不新增后台轮询、预取、变化播报或启动联网。

后续命令层可基于同一结构化结果制作图片、文字和 Markdown，无需重新取数。

## 2. 全局冷却的明确语义

### 2.1 共用范围

“全局”指当前插件实例内的所有用户、群聊和平台共用一个控制器，而不是每用户或每功能单独计时。

| 请求 | 是否占用同一 Atlas 冷却 |
|---|---|
| Atlas 匹配时间，统一数据范围 | 是 |
| 未来 Atlas 玩家昵称搜索、账号详情、查询时刷新 | 是，每次实际 HTTP 请求分别占用 |
| 匹配时间有效缓存命中 | 否 |
| 加入同一匹配时间查询的在途请求 | 否，只算底层一次请求 |
| tarkov.dev 玩家快照和昵称名单 | 否 |
| 现有服务器状态、Boss 数据和头像 | 否 |

本轮不做跨进程、跨机器人实例或同一出口 IP 的分布式协调。多个实例仍可能共用上游 IP 额度。

### 2.2 准入与计时

建议普通冷却默认 **5 秒**，配置允许 **1～300 秒**，不能设为 0。该值是本地设计建议，不是 Atlas 作者规定，最终以维护者决定为准。

- 使用单调时钟计算剩余时间，避免系统时间校准导致提前放行。
- 在实际 HTTP 请求启动前，原子检查并占用冷却；参数错误和关闭状态检查先于准入。
- 相邻实际请求的开始时间至少相隔配置秒数；同时最多一个 Atlas HTTP 请求在途，避免慢请求期间叠加并发。
- 请求开始后失败、超时或被取消，已占用的冷却不退还；在获取准入前被取消则不占用。
- 共享入口保留可识别的暂不可请求状态和 `retry_after_seconds` 供内部编排，不将其直接作为匹配时间的用户回复；匹配服务优先按缓存结果正常输出。无可用缓存且无法取得结果时才报告查询失败。不创建无界等待队列、不自动重试。
- 冷却中有有效缓存时仍然返回缓存；缓存不可用时才将冷却错误交给调用层。
- 匹配时间所有调用共用一份缓存和一个在途任务，合并后才竞争全局准入。匹配独立的 15 分钟冷却不占住未来玩家查询 15 分钟；两类实际请求仍共用 Atlas 入口的短间隔与上游暂停。
- 一个调用者取消不取消其他调用者需要的共用请求；插件关闭会取消底层任务并等待回收。

取舍：匹配冷却期间返回缓存，避免群聊重复访问上游；未来玩家“搜索后查详情”的两次实际请求仍不能紧接着发送。后续玩家编排必须显式处理冷却，不能通过新建客户端或内部重试绕过。

### 2.3 上游退避

- Atlas 任一纳入范围的接口返回 429，都更新同一个控制器的上游暂停时间，匹配时间与未来玩家请求一并遵守。
- 有效 `Retry-After` 支持秒数和 HTTP 日期；暂停到期前不再发请求。建议保守地将其他明确带 `Retry-After` 的临时服务错误也纳入同一暂停。
- 实际可再次请求时间取“普通冷却结束”和“上游暂停结束”中的较晚者；新的较短暂停不能缩短原有暂停。
- 缺失或无效 `Retry-After` 时建议默认暂停 60 秒；不把无效头解释成可以立即重试。若头指定更长时间，不为方便而截短等待。
- 结构化错误保留 HTTP 状态、受控错误码和剩余时间。未来玩家接口可区分 `busy` 与 `rate`；本轮不依据未经验证的玩家响应实现额度扣除。
- 不自动重试。总规划中玩家 `busy` 的有限重试策略留到玩家接入阶段决定，重试也必须走同一控制器。

普通冷却不能代替 Atlas 玩家查询的每分钟 20 次、每小时 200 次限额。5 秒间隔仍可能超过小时额度，未来玩家功能上线前必须补充总预算与用户限额。控制器预留在准入阶段加入预算检查的位置，本轮不提前实现未使用的计数系统。

### 2.4 生命周期与限制

控制器由插件创建一次，再注入匹配时间服务和未来玩家服务；禁止每次调用创建独立控制器。冷却、暂停和在途状态本轮只在内存中保存，插件重载或进程重启会清空；不能将重载当作绕过上游暂停的手段。后续如需跨重载保留 429 暂停，单独增加持久化，不将单调时钟值写进数据库。

## 3. 匹配时间数据契约

内部 API 建议为 `await matching.get()`，通过结构化结果或 `QueryError` 子类返回；不返回平台消息组件。

- 为落实“全部用户共用一个查询”，本轮建议固定请求 `hours=24`，所有调用读取同一份结果，不开放调用者指定小时数。24 小时沿用总规划的建议，仍是方案选择；未来可变范围需求另行设计，不能用不同 `hours` 绕过 15 分钟冷却。响应的 `hours` 必须与实际请求一致。
- 结果包含 `hours`、上游 `server_time`、上游采样时间 `updated`、本地 `fetched_at`、`from_cache`、`stale`，以及数据中心和历史数据。
- 数据中心保存地区代码、原始名称、仅合并首尾/连续空白后的显示名称、等待秒数。原始名称用于连接 `history.series`，避免名称规整导致串线。
- 不自行删除 `Sa`、`Me`、`Af` 等名称前缀，不增加未经确认的中文地名映射。
- `wait` 接受非负有限数值，拒绝布尔值、负数和字符串；`null` 保留为缺失，0 秒保留为有效 0。
- 历史保存 `start`、正整数 `step` 和各数据中心的序列，按 `start + index * step` 解释时间；序列里的 `null` 保留断点，不填 0、不插值。
- 时间戳必须可以安全解析；JSON 非有限数值、错误根类型、重复数据中心身份、无效历史结构等作为数据错误，不能覆盖上一份有效结果。
- 未知额外字段忽略；历史缺少某个中心的序列时保留该中心的当前值并标记历史缺失，额外历史序列不凭空新增当前中心。
- 设置合理的中心数、名称长度、每条序列长度和总点数上限；建议初始上限为 128 个中心、名称 128 字符、每条 1024 点，允许上游现有 28 个中心、最多 288 点的小幅增长。
- 返回不可变数据，或为每个调用者复制可变内容，避免一个调用者修改共享缓存。

## 4. 全局匹配缓存、独立冷却与合并

- 全部用户、群聊和平台共用一个匹配服务、一份最近成功结果和一个在途任务。本轮不按用户、群聊或小时数分别建缓存，不新建 SQLite 表。
- **匹配时间独立冷却为 15 分钟（900 秒），也是成功缓存有效期**。成功获取并通过校验后开始计时；15 分钟内所有额外查询直接返回同一份缓存，不联网、不延长窗口、不输出“冷却中”或剩余时间。
- 15 分钟结束后，由下一次用户查询按需刷新；没有查询就不刷新，不做后台轮询。并发刷新合并为一次请求；有可用旧缓存时其他调用可以直接读取旧缓存，无缓存的首次并发调用共用请求结果。
- 刷新失败不覆盖成功结果、不更改其获取时间。**旧缓存回退上限为自最近成功获取起 60 分钟（3600 秒）**，不是过期后再加 60 分钟，也不是每次读取重新计时。
- 网络失败、429、5xx、格式错误或共享 Atlas 入口暂不可请求时，存在上限内的成功结果就按缓存结果输出，携带 `from_cache=True`、`stale=True`、原采样/获取时间及内部受控原因，不将本次刷新失败改成用户可见的失败回复。
- 没有缓存、缓存已超过 60 分钟且本次取数失败，才返回查询失败。参数错误、功能关闭、无效代理和程序错误仍按相应错误处理，不能用旧结果掩盖配置或调用问题。
- 防止失败后每条查询重复访问：一次匹配 HTTP 尝试结束后，即使失败，也设置独立的下一次可尝试时间为完成后 15 分钟；失败窗口内有 60 分钟以内的旧结果就输出缓存，否则返回查询失败。上游 `Retry-After` 更长时仍须遵守更长暂停。失败后的 15 分钟退避是本规划建议的补充选择，尚未实现。
- 缓存年龄与独立窗口分别保存。失败可以更新下次允许尝试时间，但绝不能更新成功缓存年龄，使旧结果无限续期。
- 15 分钟独立窗口不阻止未来 Atlas 玩家查询；未来玩家只受共用入口短间隔、上游暂停和届时增加的玩家限额约束。
- 不提供绕过缓存的刷新接口。上游 `max-age=60` 不缩短本地 15 分钟窗口；结果如实携带采样时间与缓存标记，不能声称是实时数据。
- 上游 `updated` 与本地缓存年龄分别保留，刚获取的结果也可能来自上游旧采样，后续展示层必须显示采样时间。

取舍：所有会话共享缓存可以严格减少访问；代价是数据最多在下一次窗口开放后才更新。内存缓存重启丢失，本轮不承诺跨重启保留 15 分钟窗口或旧结果。

## 5. 模块与现有代码衔接

| 文件（拟） | 职责 |
|---|---|
| `tarkov_core/atlas_client.py` | 固定 Atlas 主机、匹配路径白名单、参数编码、HTTP 请求和错误归一；持有共享控制器，预留未来玩家入口 |
| `tarkov_core/atlas_cooldown.py` | 普通冷却、在途互斥、共享上游暂停、可注入时钟和结构化拒绝 |
| `tarkov_core/matching.py` | 数据模型、响应规范化、单份全局缓存、15 分钟独立冷却、请求合并、有限旧缓存回退 |
| `tarkov_core/settings.py`、`_conf_schema.json` | 新增 Atlas 设置组及参数读取 |
| `main.py` | 创建和注入单例服务、关闭回收；不增加命令路由 |
| `tests/test_atlas_client.py`、`tests/test_atlas_cooldown.py`、`tests/test_matching.py` | 后端契约、并发与错误回归 |

现有 `transport.http_get()` 的错误文案固定为 tarkov.dev，429 时也不读取错误 JSON；不能直接用于 Atlas 后宣称错误语义已兼容。实施时复用现有 `HTTPClient` 连接池及显式代理校验，Atlas 单独处理错误响应；如提取有界读取/解压工具，保持原调用默认行为并补回归测试，避免为新接口大改现有链路。

HTTP 约束：仅 `https://www.eftforge.com`，不跟随跳转、`trust_env=False`、不使用 Cookie、不接受用户或返回数据指定的 URL、不自动拉取头像或其他资源。建议匹配请求总超时 30 秒，压缩/解压上限分别 2 MiB/8 MiB，错误体上限 64 KiB；仅接受 JSON，限制 gzip 解压输出。异常文本不得泄露代理凭据或直接转发上游错误体。遇到超过可安全表示的 `Retry-After` 时保持禁止请求并返回受控错误，不能截短后提前重试。

代理沿用插件已有显式代理设置；配置开启但地址无效时在准入前拒绝，不占用冷却、不静默直连。配置中文说明应同步覆盖 Atlas，避免仍写成只访问 tarkov.dev。

## 6. 设置建议

| 设置键 | 默认值 | 说明 |
|---|---|---|
| `matching_enabled` | `false` | 匹配时间功能开关；关闭后调用服务返回未启用且不联网、不提供旧缓存 |
| `matching_cache_seconds` | `900` | 匹配时间独立冷却与成功缓存有效期；本轮按维护者要求固定 900 秒，不开放配置修改 |
| `atlas_query_cooldown_seconds` | `5` | 两类 Atlas 请求共用的间隔，1～300 秒 |

匹配独立窗口 900 秒、旧缓存最大 3600 秒、请求超时和容量上限本轮作为实现常量；上表 `matching_cache_seconds` 仅说明内部命名，不新增可修改设置，避免与固定 15 分钟需求冲突。缺失配置使用默认值；非法类型、布尔值冒充数字、NaN/Infinity 和越界值按统一校验回退并记录受控警告，不能造成无冷却。

## 7. 开发顺序与验收

1. 共享冷却：先用可控时钟测试原子准入、并发、取消、普通冷却与 `Retry-After` 叠加。
2. Atlas HTTP 入口：固定主机与路径、显式代理、读取限额、超时、JSON 和错误映射；用本地假服务器或可注入传输验证。
3. 匹配模型与服务：虚构响应、规范化、单份缓存、15 分钟窗口、合并、60 分钟旧缓存和错误边界。
4. 配置和生命周期：插件创建后不联网，启用查询时才请求；关闭时停止并 await 自有任务，再释放所用 HTTP 资源。不得关闭仍被现有功能使用的共享连接池。
5. 回归：新增有意义的自动测试并运行现有测试；同步 handoff 和 checklist。真实匹配接口可最后做一次只读烟测，但自动测试不依赖外网，也不请求真实玩家档案。

关键验收场景：

- A 用户成功查询后，B 用户及其他群聊在 15 分钟内均读取同一份结果，不再访问 Atlas；模拟的未来玩家查询不受匹配的 15 分钟窗口限制，但遵守共用短间隔与上游暂停。现有状态、Boss、tarkov.dev 查询不被拦截。
- 首次查询和过期刷新各有 20 个并发调用时，底层均至多发一次请求；本轮不开放不同小时数查询。
- 命中缓存时不占用共用请求入口、不延长独立窗口；第 900 秒前读缓存，窗口到期后下次调用才触发刷新。
- 刷新失败时，59 分钟的成功缓存仍正常输出；超过 60 分钟的旧缓存不能继续输出。失败后的独立窗口与成功缓存年龄分别计算，不能读一次续期一次。
- 冷却中有可用结果按缓存正常输出，不出现“请等待 N 秒”；仅无可用结果且查询无法完成时报告失败。
- 429 的暂停覆盖两类入口，遵守更长的 `Retry-After`，失败不退还普通冷却；不出现自动重试循环。
- 匹配结果的 `null`、0、名称空白、历史断点、更新时间都可被后续展示正确区分。
- 无效响应不污染有效缓存，旧缓存有年龄上限和来源标记；无效代理、关闭功能不能用缓存掩盖。
- 个别调用取消不破坏其他调用；插件关闭后无遗留请求、无人接收的任务异常或已关闭连接池复用。

## 8. 已确定要求与剩余建议

维护者已确定：全部用户和群聊共用匹配结果；匹配独立冷却/缓存有效期 15 分钟；失败最多回退到 60 分钟内的成功缓存；冷却期间按缓存正常输出，无可用结果时才报告查询失败。

仍为规划建议：共享 Atlas 请求短间隔 5 秒、最多一个 HTTP 请求在途、固定 24 小时历史范围、失败后也退避 15 分钟。以上均尚未实现。

本轮不依赖匹配命令名、图片样式、玩家刷新写法或玩家成功样本；这些问题不阻塞后端实现。


## 9. 后端实现与验证（2026-11-08）

- 已实现 `AtlasClient`、`AtlasCooldown` 和 `MatchingService`，插件通过 `self.matching.get()` 调用，默认关闭；配置项位于 Atlas 组。未来玩家 HTTP 方法须复用 `self.atlas` 的准入逻辑。
- 本轮固定请求 24 小时历史，一份内存缓存供所有用户和会话共用；成功后 900 秒内直接返回缓存。缓存到期由查询触发刷新，失败后独立退避 900 秒，成功结果年龄超过 3600 秒不可回退。缓存年龄用单调时钟判断，结果保留上游采样时间和本地获取时间。
- Atlas 共用短间隔默认 5 秒、允许 1～300 秒，严格校验配置；同时最多一个实际请求。429 与带 Retry-After 的 5xx 更新共享暂停，不自动重试，也不缩短较长的上游暂停。
