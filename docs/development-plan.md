# 下一阶段开发方案：状态、物品、Boss 刷率与 QQ 官方机器人

日期：2026-10-24；工作分支：`1024`。本版已按维护者最新要求重整：所有查询输出图片、所有轮询间隔可调、物品通用/模式数据分开、Boss 全表变化标红、100% 刷率红字加粗。方案分阶段实现，未落地的配置键名和未指定的默认值仍为建议；当前进度见第 11～14 节。

## 1. 目标与基本约定

本轮新增四组能力，每组都有设置开关。将“用户主动查询”和“后台定时播报”拆开：开查询不自动订阅群聊，开播报不向所有允许使用插件的聊天群发。已有玩家查询、绑定关系和数据缓存保留，玩家查询输出同步纳入统一图片规范。

- 公共数据统一走 JSON API，不依赖维护模式的 GraphQL；数据范围及请求格式见 [API 参考](tarkov-api-reference.md)。
- 新数据功能默认关闭，管理员逐项启用；功能关闭后不下载对应数据，不启动对应后台任务，命令只提示功能未启用。共享资源被其他已启用功能使用时仍可刷新。
- QQ 兼容开关控制新增的命令/输出适配，建议默认开启；关闭时回到现有处理方式，不直接禁用已有 QQ 查询。
- 查询复用现有 `access_mode`、`user_whitelist`、`allowed_origins`。播报目标另用明确的 UMO 列表，不把 `allowed_origins` 当订阅名单；目标列表为空表示不发送。
- 设置播报、测试播报和修改目标仅允许 AstrBot 管理员。群管理员身份不自动等于 AstrBot 管理员。
- 接口超时/拒绝访问表示本次获取失败，不表示游戏停服、Boss 刷率归零或物品不存在。
- 所有查询通过图片返回，包括玩家档案、状态、物品、Boss 表格、变化摘要、候选列表和无结果/查询失败提示；帮助沿用图片。成功查询不能自动降级为完整文字/Markdown 报告。图片生成或发送也失败时仅给简短错误提示，避免静默无响应。绑定/解绑等操作确认可继续用短文字。
- 状态与 Boss 播报也使用图片；文字只作为允许发送的链接、页码等补充，不承载主要查询结果。
- 所有后台数据轮询都提供独立间隔设置，范围统一为 2～30 分钟；这决定正常检查频率，不保证上游在同样频率更新数据。

## 2. 设置设计

第一版沿用现有扁平配置 schema，中文说明中写明父开关依赖和关闭后的行为。

| 建议配置 | 默认值 | 控制内容 |
|---|---|---|
| `status_enabled` | `false` | 服务器状态查询总开关 |
| `status_broadcast_enabled` | `false` | 状态后台轮询与变化播报，依赖状态总开关 |
| `status_qq_push_enabled` | `false` | 状态播报到 QQ 官方会话的独立许可；仍依赖适配器能力与实际平台权限 |
| `items_enabled` | `false` | 物品查询总开关 |
| `item_flea_enabled` | `true` | 物品跳蚤市场价格子功能，依赖物品总开关 |
| `item_trader_enabled` | `true` | 商人买卖价格子功能，依赖物品总开关 |
| `item_details_enabled` | `true` | 通用属性和模式属性差异核对，依赖物品总开关 |
| `item_images_enabled` | `true` | 物品卡片中的可选缩略图，依赖物品总开关 |
| `boss_enabled` | `false` | Boss 当前刷率/变化摘要查询总开关 |
| `boss_broadcast_enabled` | `false` | Boss 后台轮询与变化播报，依赖 Boss 总开关 |
| `boss_qq_push_enabled` | `false` | Boss 播报到 QQ 官方会话的独立许可，与状态播报开关独立 |
| `qq_official_compat_enabled` | `true` | QQ 官方适配，包括 `@机器人 /命令`；默认不改变其他平台 |
| `short_commands_enabled` | `true` | 注册 `/status`、`/item`、`/boss` 短命令；冲突时可关闭 |
| `status_poll_minutes` | `5` | 状态轮询间隔：2～30 分钟，整数步长 1 |
| `boss_poll_minutes` | `10` | Boss 轮询间隔：2～30 分钟，整数步长 1 |
| `boss_modes` | `["pvp", "pve", "season"]` | 要监控的模式，转换为 API 的 `regular/pve/pvp-season`；每个所选模式输出全部地图、全部 Boss |
| `status_notify_targets` / `boss_notify_targets` | `[]` / `[]` | 两类播报分别配置目标 UMO |
| `notify_cooldown_seconds` | `60` | 每类事件、每个目标的最短发送间隔，期间合并变化 |
| `notify_quiet_hours` | 空 | 可选免打扰时段，明确配置时区；结束后发最新汇总 |
| `public_data_cache_minutes` | `5` | 公共资源按需缓存有效期，不是后台轮询；过期后由查询触发条件复查 |
| `qq_link_policy` | `configured` | QQ 链接策略：仅使用已配置允许的链接；另提供不带外链的输出选项 |

子开关默认 true 的含义是“启用物品总开关后可使用”，不是默认下载物品数据。总开关关闭时，子开关均不生效。`item_details_enabled` 控制通用属性和跨模式属性差异，另外两项控制显式模式查询的价格区块；关闭属性核对后，显式模式价格查询只加载所选模式。关闭任一价格区块仍可展示已开启的属性区块。没有任何可展示区块时返回图片提示，避免空卡片。缩略图开关只控制卡片内的物品图片，关闭后查询结果仍为图片。

现有 `output_mode` 在本轮统一图片要求下不再提供文字/Markdown 查询选项；已有这两种值的配置迁移为图片，不保留“图片失败自动输出完整文字结果”的行为。图片是查询结果的固定形式，功能是否启用仍由各项开关控制。

轮询间隔在配置页使用滑块（min=2、max=30、step=1）并显示单位“分钟”。保存后更新现有调度器：重算下一次检查时间，不重复创建任务，不对错过的周期补跑。每轮不重叠；请求失败的退避/限频等待可延长实际间隔，恢复后回到配置频率。后续新增后台数据刷新任务也必须配置自己的 2～30 分钟间隔，不引入隐藏的固定频率轮询。

播报有效条件：总开关开启 + 播报开关开启 + 有符合会话限制的目标。没有有效目标时不启动专门用于播报的轮询，并在插件日志/管理状态中说明。只有查询开关时按需拉取数据。

`short_commands_enabled` 必须控制框架实际路由参与情况，不能只在 handler 中拒绝，因为拒绝也可能抢占其他插件命令。实现时核对受支持 AstrBot 版本的命令管理能力；若需重载才生效，在设置中明确说明。

## 3. 命令与交互

| 用途 | 非 QQ 平台示例 | QQ 官方群聊示例 |
|---|---|---|
| 当前服务器状态 | `/status` | `@机器人 /status` |
| 物品通用属性图片 | `/item Salewa` | `@机器人 /item Salewa` |
| 指定模式数据图片 | `/item pve Salewa` | `@机器人 /item pve Salewa` |
| PVP 独特数据图片 | `/item pvp Salewa` | `@机器人 /item pvp Salewa` |
| 赛季独特数据图片 | `/item 赛季 Salewa` | `@机器人 /item 赛季 Salewa` |
| 指定物品 ID | `/item pve id:544fb45d4bdc2dee738b4568` | `@机器人 /item pve id:544fb45d4bdc2dee738b4568` |
| 全部监控模式的 Boss 全表图片 | `/boss` | `@机器人 /boss` |
| 指定模式的 Boss 全表图片 | `/boss pve` | `@机器人 /boss pve` |
| 查看最近变更的完整表格图片 | `/boss 变化` | `@机器人 /boss 变化` |

同时提供稳定的命名空间入口：`/tarkov status`、`/tarkov item ...`、`/tarkov boss ...`。短命令发生冲突时保留这些入口。中文别名可加入“状态/物品/刷率”。解析新增子命令时保留原有玩家查询路径；玩家昵称恰好与新子命令同名时可通过显式模式或账号 ID 查询。

`/status` 是机器人命令；它调用的是数据服务的 `https://json.tarkov.dev/status`。两者不要在代码命名中混淆。

物品名可包含空格，不复用当前玩家昵称的单 token / 字符集限制。`/item <名称>` 只查通用属性，不套用默认模式，不显示某个模式的价格；`/item <模式> <名称>` 查该模式独特数据，不自动回退到别的模式。先识别可选模式和 `id:` 前缀，再把剩余全文作为名称；首版不要求额外输入“跳蚤/商人/属性”子命令。模式词与物品名产生歧义时允许用引号标记完整名称或用 `id:` 查询，不能静默误判。

## 4. 服务器状态检查与播报

数据源：`GET /status`。读取 `generalStatus`、`currentStatuses`、`messages`。

### 查询

返回服务器状态图片：顶部整体状态，主体为认证、匹配、交易、背包等组件状态表，底部为最近相关公告、获取时间与缓存情况。整体正常也输出图片；异常组件突出显示。对已知状态码提供中文名称，未知状态保留原码，不能默认解释为正常。

当前样本中 `currentStatuses` 也包含 Global，应与 `generalStatus` 去重。组件优先按 `_id` 标识，没有 ID 时按规范化名称回退。公告按 ID 去重，正文为空时不发送空公告。

### 轮询

1. 第一次成功只保存基线，避免启动时向所有目标播报一次现状；管理员可主动 `/status` 查询。
2. 后续成功结果规范化、排序后比较状态；不比较数组顺序、获取时间或无关格式变化。
3. 整体/组件状态变化或新增有效公告生成事件，以状态图片播报；故障和恢复均可播报，相同状态不反复发送。
4. 请求失败保留上次成功基线；按退避重试，日志记录监控失联；不生成“游戏停服”事件。
5. 播报标注“上游公开状态发生变化”，不声称从插件服务器直接验证了每个游戏服务可用性。

状态检查默认每 5 分钟一次，可在设置中独立调为 2～30 分钟。播报图包含变化前后状态、当前组件表和检查时间。

## 5. 物品对象、价格和属性查询

数据源：各模式的 `/items`；需要展示商人名时加载对应模式的 `/traders`。翻译分别获取 `_zh` 与 `_en`，并按响应中的 JSONPath 处理。材料和物品关系保留 ID，不修改上游对象。

### 通用属性与模式数据分层

统一使用同一个物品 ID 连接 PVP/PVE/赛季数据，维护 `CommonItem` 和 `ModeItemData(mode, itemId)` 两层。跨模式共享的是物品身份及核对后的共同字段，不能共享带模式的价格对象。

- `/item <名称>`：输出通用属性图片。白名单候选包括名称、ID、图片、重量、占格、分类，以及弹药伤害/穿深、护甲等级/材质、药品治疗参数等类型属性；只有在各模式可用快照中一致且完成所需模式核对后，才标为共同属性。
- 初次构建通用对象时按需下载三个模式并建立缓存；跨模式核对与索引构建放在线程执行，后续按需条件复查。部分模式获取失败时说明“通用属性跨模式核对未完成”，只展示已能确认的身份信息，不把 regular 的值伪装成三模式共同属性。
- `/item <模式> <名称>`：输出该模式数据图片，顶部仅保留识别物品所需的名称/ID，主体展示跳蚤价格、商人买卖报价、购买/解锁/交易限制，以及确实与其他模式不同的属性。公共属性不在主体中重复堆叠；可以提示通用属性查询命令。
- 字段在模式间不一致时不进入共同字段集合；显式模式图片注明差异及对比依据。区分字段缺失、明确为 0、不适用和接口失败，不把它们当成相等。
- 当前未完成对比时，显式模式仍可展示已获取的该模式价格及条件，但不能把未核对的属性断言为独有。某物品不在该模式里时返回图片说明，不显示其他模式的价格。

### 查询对象与索引

新增独立 `ItemCatalog`，维护物品对象与中文名、英文名、简称、`normalizedName` 索引。匹配优先级：显式 ID → 名称精确匹配 → 忽略大小写匹配 → 包含匹配。候选结果也绘为图片，列出名称、ID 及下一步命令；不把同名候选直接当成唯一结果。通用查询用跨模式索引，指定模式查询用该模式索引。

优先采用本地 SQLite 搜索索引和原始 JSON 磁盘缓存；按模式延迟加载，数据解析/建索引放到线程中，同一资源的并发请求合并。索引重建成功后原子替换；失败保留旧版本。中文词典与基础数据各自维护版本和 ETag。

### 两类图片的内容

- 跳蚤价格：最新扫描最低价、24 小时均价/最低/最高、报价数量及扫描时间。无报价、禁跳蚤、未解锁条件分开显示；不是逐笔成交记录，也不是承诺当前立即能买到。
- 商人价格：分“从商人购买”和“卖给商人”；显示原币价格、折合卢布、商人等级、任务解锁、限购。条件性最优报价必须带购买条件，不假装对所有玩家可用。
- 通用属性图：名称、占格、重量、类别和物品 ID；不出现默认模式或任意模式价格。
- 属性按 `propertiesType` 展示并进行共同字段核对：弹药看伤害/穿深/初速；护甲看等级/耐久/材质；枪械看人机/后坐力/射速；药品看治疗/使用时间/效果。缺字段不填造数值；有模式差异的字段移入模式图。

首版不增加制造利润、易物利润或历史价格画图命令；它们需要各自的成本模型和设置开关，可在基础物品查询稳定后独立扩展。

分别构建通用属性卡片和模式数据卡片，并在首版同时实现图片 renderer；图片不是后续补充项。主结果尽量一张图，内容超长时按完整区块分页；页脚标明模式或“通用属性”、对比/扫描时间和来源。图片失败时只发简短错误提示，不自动改发完整文字结果。

## 6. Boss 刷率变化轮询播报

数据源：每个所选模式 `GET /{mode}/maps`，Boss 名称通过 `mob` 连接 `data.mobs`。`maps.bosses` 也会列出普通 AI，不能直接将所有记录当作日常 Boss。

### 最终监控范围（维护者修正）

仅包括 Tagilla、Reshala、Shturman、Sanitar、Killa、Glukhar、Zryachiy、Kaban、Kollontay、Partisan、邪教徒祭司，以及三狗（GOONS）。使用稳定 `mob ID` 白名单；Knight 的概率代表 GOONS 小队，展示名称固定为“三狗（GOONS）”，不另外列 Big Pipe/Birdeye。BEAR、USEC、护卫及名单外活动变体均不入表。地图排除破冰船、原中心区、实验室 Dark、迷宫和中心区教程；原中心区 21+ 保留其独立数据并显示为“中心区”。无目标 Boss 的单元格留白，不填 0%。

### 快照和比较

内部仍以模式、地图 ID、Boss ID 和规范化刷新规则识别记录。同一 Boss 的多条记录完整保留，不盲目相加；相同条件才能直接比较概率。条件或记录增删可以触发记录变化，坐标、图片、翻译及数组排序不触发刷率变化。概率要求 0～1 有限数值，拒绝空值和布尔值；按 12 位小数处理尾差，接近 0/1 的数值保留边界差异。

每模式使用最近两次成功快照比较，首次静默。手动查询不推进监控基线，304 复用已规范化状态且不生成新事件；缓存读取仍校验 JSON。格式错误、超时和旧数据不推进基线，不生成归零事件。新增模式首次建基线，停用模式退役基线及积压。范围或表格版本升级时清理旧基线/事件/续查快照，避免旧图继续出现普通 AI，以及范围调整被误报成刷率变化。

### 深色矩阵（维护者参考图）

采用参考图的深色矩阵：**Boss 为行、地图为列，交叉单元格显示刷率**，左上角显示模式。左侧固定展示 12 类目标 Boss 及头像，地图列保持约定范围，当前为 12 张地图；仅保留原中心区 21+ 的数据，列名为“中心区”，不合并原中心区数据。刷新条件、上次概率及变化说明均不设列。

同一单元格内的不同概率分别显示，不相加；相同概率可以显示去重，内部仍完整保留记录。未列出为留白，明确 0% 则显示 0%。事件中移除记录可以用红色横杠标记。本次变动标红；100% 数值与对应 Boss 名称固定红色粗体，首次或未变化也标注。混合概率只将实际 100% 单独加粗，不能把接近 100% 的值四舍五入成 100%。

头像来源为 `data.mobs[BossID].imagePortraitLink` 指向的 assets.tarkov.dev 文件，三狗使用 Knight 头像。**仅设置项 `boss_portraits_update` 手动拉取/更新**，保存重载执行一次且执行前自动复位并保存；缓存有效期 365 天。查询、轮询、普通启动、缺失或过期均不自动下载；缺失/过期显示占位图，手动更新失败保留仍有效的旧头像。头像不随源码包分发。

每模式独立制表，一页最多 16 个地图列，必要时按列分页、重复 Boss 行，保证全部地图可续查。图上保留模式、检查/对比时间、来源和页码。每次查询回复一页及固定快照续查命令 `tarkov boss 页 <编号> <页码>`，避免依赖 QQ 被动窗口一次发多图。`/boss [模式] 变化` 复用最近事件冻结矩阵及标红，普通查询和 304 不改写对比基准。

### 轮询和播报

`boss_poll_minutes` 默认 10 分钟，可独立调为 2～30 分钟。每个目标共用一次数据检查，不按群重复请求。源站失败退避，不重叠或补跑；一个模式失败不阻止其他模式保存并提交成功变化。

播报按完整表格逐目标、逐页跟踪，每目标每轮最多 5 页，剩余页下轮继续。失败只重试未完成页，部分页提交不能记为整组送达；明确权限错误暂停目标，未知结果不伪造送达回执。先关闭播报保存重载、修复设置/权限，再开启保存重载可清除暂停与积压，重新建立静默基线。

这是上游公布的数据变化，不提供当前房间的 Boss 实时位置，也不使用社区目击报告推算概率。

## 7. QQ 官方机器人兼容

### 命令接收

在现有 `command_style` 增加 `mention_slash`：帮助和提示统一显示 `@机器人 /tarkov` 等命令，同时保留 `mention`、`slash`。`command_style` 只决定提示格式，真实接收逻辑单独处理。

优先使用 AstrBot 的 qqofficial / qqofficial_webhook 适配器产生的消息组件：辨认真实 At 组件，获取去除自身 mention 后的文字，并规范化命令开头可选的 `/`。不要把用户输入的字面文本“@机器人”当作真实提及，也不要全局删除内容中的斜杠或 URL。

关键检查点在框架路由之前：仅修改本插件 `COMMAND` 正则不能修复“框架没有把 `/status` 分配给 handler”。先验证 AstrBot 的 `wake_prefix`（建议包含 `/`）及命令过滤器；确有旧版差异时用仅作用于 QQ、已唤醒且精确命中本插件命令的适配入口，所有入口统一走权限和功能开关检查，避免重复处理或绕开框架权限。测试真实 WebSocket/Webhook 事件。

### 回复与播报

- 普通查询沿触发事件回复，交给 AstrBot 维护 `msg_id`/序号及图片上传；不自己实现 QQ 登录或鉴权。
- QQ 的链接和富媒体能力取决于机器人后台配置。所有查询仍然输出图片，增加 QQ 专用上传/分页与链接策略；不对未配置的域名反复重试，也不承诺图片后附带链接一定可发。平台拒绝图片时仅报发送失败，不以完整文字/Markdown 报告代替。
- 图片内容可保留数据来源；不能发可点击链接时，帮助明确说明该会话使用无外链回复。其他平台继续保留文本链接。
- QQ 主动播报列为能力依赖：下述官方资料存在版本差异，不能把当前 master 的支持推定为本仓库最低版本 AstrBot 4.16.0 或所有机器人都支持。
- 新版 AstrBot 文档声明可在群设置允许主动发言后推送；旧腾讯公开文档仍包含主动推送停用声明。实现采用版本/场景能力检查和管理员明确配置，在实际目标群验证权限和发送结果后启用；不复用过期用户消息伪造长期被动回复资格。
- 不支持主动推送的会话保留查询能力，用户通过 `@机器人 /status`、`@机器人 /boss 变化` 查看当前状态和已记录摘要；不把“订阅已保存”显示成“主动推送可用”。

### 验收环境

至少覆盖 QQ 官方 WebSocket、Webhook 的群聊和私聊；真实提及 + `/命令`、无斜杠旧命令、单图/多页图片/图片失败提示、URL 允许/不允许、主动消息允许/拒绝，以及另一个已有平台的回归。多页输出需核对被动回复窗口与可用次数；页组超出场景限制时，在保持可读且不漏行的前提下合并地图分页或提供带稳定快照页号的图片续查命令，不能假定页数无限，也不能无说明截断。没有实机验证时，发布说明必须标记范围，不能只凭 SDK stub 宣称适配完成。

## 8. 共用实现结构

建议拆出下列模块，避免继续把所有功能放进 `main.py`：

| 模块 | 职责 |
|---|---|
| `public_api.py` | 固定 JSON 主机、路径白名单、HTTP 校验、ETag 条件请求、代理、并发合并和限流 |
| `resource_cache.py` | 按模式/语言保存资源、原子替换、索引版本、获取时间和旧缓存回退 |
| `server_status.py` | 状态规范化、展示、变化比较 |
| `items.py` | 物品索引、名称匹配、商人关联和卡片数据 |
| `query_images.py` | 状态、通用物品、模式物品、候选/提示图片及统一页脚 |
| `boss_monitor.py` | 模式/地图/Boss 条件化快照、变化检测 |
| `boss_table_image.py` | 全地图全 Boss 表格、红色变化标记、可读字号与分页 |
| `polling.py` | 所有轮询的独立 2～30 分钟设置、重调度、退避与取消 |
| `notifications.py` | 目标过滤、持久化待发送事件、合并、去重、重试和平台能力 |
| `platform_compat.py` | QQ 命令入口及输出策略 |
| `main.py` | 注册命令、权限检查、生命周期和调用编排 |

公共数据传输可复用 gzip、超时和代理校验思路，但不直接复用玩家档案的 16 MiB 解码上限：本次物品 JSON 已约 17.3 MB、地图约 8.9 MB。为资源设置独立上限，JSON 解析、翻译和建索引放在线程中，控制大资源同时加载数量。

新增独立监控数据库保存成功基线、变化事件和每个目标的投递状态，不混入账号绑定表。建议 7 天事件保留期和有界待发送队列；静默期合并成最新摘要，防止恢复后刷屏。合并摘要保留期间发生过异常及恢复的事实，不能只看最终净变化而吞掉“正常 → 异常 → 正常”的过程。手动查询变化只能展示已记录事件，不能重建没有轮询期间的完整历史。

基线更新与新事件入队在同一 SQLite 事务中完成；发送成功后仅标记对应目标，某个群失败不重发给其他已完成目标。临时错误有限重试、权限错误暂停该目标并提示管理员处理。外部 API 发送成功后本地确认前崩溃仍可能重复，因此不承诺严格 exactly-once。

AstrBot 的 `context.send_message()` 返回值表示是否匹配到平台，不等于用户已收到消息。适配器明确报错要保留失败；适配器静默跳过或没有确认的发送只能记录尝试/未知，不能伪造送达回执。

后台任务由插件生命周期统一创建、记录、取消并 await；禁止每个目标启动一套轮询。重复初始化不能重复启动；配置重载时先停止旧任务。大资源线程任务完成后也要检查实例/配置版本，避免旧实例重新发布过期索引或事件。

## 9. 建议实施顺序与验收

1. **公共基础与 QQ 路由验证**：定义配置和路由、公共 API 客户端、资源缓存；验证真实 `@机器人 /命令`；修复 handoff §25 的失败/不存在混淆，统一失败语义。
2. **状态查询，再接入播报骨架**：完成 `/status`；引入状态基线和变化事件，先使用可确认支持主动消息的平台验证，不将 QQ 推送作为普通查询的前置依赖。
3. **物品两类图片查询**：完成名称/ID 查询、跨模式共同属性核对、商人关联、中文回退、模式价格/限制/差异属性；通用图、模式图与候选图同步交付。
4. **Boss 轮询与图片播报**：复用缓存和播报模块，完成条件化概率差异、全地图全 Boss 表格、变化标红、分页、重启去重、静默与恢复汇总。
5. **QQ 官方实机验收与发布整理**：验证被动回复、平台权限和可用的主动播报范围，基于验证版本决定是否调整最低 AstrBot 版本；每阶段更新 handoff，README/checklist 留待单独整理。

关键测试以用户可见行为为准：

- 关闭开关后无专属下载/任务/推送；父开关依赖正确；权限和播报目标限制有效；短命令关闭后不抢占其他命令。
- 状态无变化静默，异常/恢复只发一次；请求失败不误报停服；组件重排不触发变化。
- 所有查询（包括已有玩家档案）输出图片，候选、无结果、查询失败也有图片；旧 text/markdown 配置迁移后仍为图片，绘制/上传失败不泄漏为整份文字结果。
- `/item 名称` 不使用默认模式、不含价格，真正的共同属性才入图；`/item 模式 名称` 展示指定模式价格/条件/差异属性，不静默跨模式回退；缺失模式不被假定与其他模式一致。
- 物品多词名称、同名候选、模式词歧义、中文缺译、不同模式不同价、币种方向、无报价和缺属性均正确；大资源超过限额时保留旧缓存。
- Boss 真正概率改变可发现；重复条件、多个刷新记录、记录增删、数组重排、格式损坏和超时均不产生错误的“0%”播报。
- Boss 图片包含所选模式所有地图和所有 Boss；未变行保留，变化值/新增/移除/规则变化标红；分页无漏行，查询和 304 不改写已有事件的对比基准。
- 每类轮询测试 2、30 分钟边界、越界/非法值、独立配置、保存后重调度、慢请求不重叠和不补跑；暂停/重启没有重复任务。用可控时钟验证，不真实等待数分钟。
- 重载无重复轮询；重启不重发已确认事件；部分目标失败只重试失败目标；静默/冷却合并不会吞掉恢复事件。
- QQ 正确的真实提及可触发、普通文本假提及不触发；框架剥离/保留斜杠的两种路径都只处理一次；输出失败/权限拒绝有明确结果。

## 12. 第二阶段进度：状态图片查询与播报基础

已接入 `/status`、`/状态`、`/tarkov status` 和 `/塔科夫 状态`。QQ 官方平台沿用真实提及后的斜杠补充入口；其他平台遵循 AstrBot 的唤醒前缀设置。状态接口是全局资源，无需模式参数。新增查询固定输出图片，包含总状态、组件列表、公告、检查/获取/上游版本时间、缓存来源；禁用、拒绝权限、参数错误与获取失败也输出提示图。只有图片生成本身失败时给简短文字错误。

`status_enabled` 与 `status_broadcast_enabled` 默认关闭，目标默认空。配置页将 `status_poll_minutes` 设为 2～30 分钟滑块，默认 5 分钟；保存重载生效。启用查询不会自动启动轮询。启用播报后仍须配置完整 UMO 目标（可用 AstrBot `/sid` 查看），最多 50 项；再与 `allowed_origins`、已知平台主动发送能力取交集。QQ 官方目标另需 `status_qq_push_enabled`，该开关不会授予平台权限。

播报仅有一个后台任务，首次成功静默；后续比较成功快照的总体/组件状态、非空总体说明和有效公告。公告正文/时间修订可形成新事件，已见公告重新出现不会重发。组件排序和显示名称调整不触发变化。轮询每轮条件复查，不受手动查询缓存 TTL 阻止；网络/格式错误或旧缓存不会推进成功基线，也不会被当作游戏故障。

`notifications.sqlite3` 独立保存基线、公告去重记录、不可变变化事件与逐目标提交状态。基线更新和事件入队为同一事务；重启沿用成功基线及未完成事件。每个目标每轮最多提交一张事件图，保留中间故障及恢复过程；某目标失败不重发给已提交目标。临时错误最多三次尝试，重试等待以轮询执行时点为准；明确权限错误暂停该目标并记日志。修复权限后关闭播报、保存重载，再开启、保存重载以清除暂停与积压并重新建立静默基线。配置移除目标会清除其待提交记录；关闭播报会退役原基线和积压。

事件保留 7 天、最多 200 条且事件载荷总计不超过 64 MiB；公告去重最多 2048 条。平台返回 `True` 只记为已提交，`None` 记为结果未知且不自动重试，不能声称用户已收到；崩溃窗口下不承诺严格一次送达。独立免打扰时段和冷却合并仍为后续功能，本阶段通过每目标每轮一张图限制积压提交速度。

短命令关闭会停用框架实际的两个状态处理器，保留命名空间入口；已用真实 AstrBot 4.16.0 注册/过滤代码验证其他插件的同名命令可继续匹配。当前自动化验证为 241 项单元/集成测试与 67 个 SDK 路由回放场景；真实公开状态 GET/条件复查及图片绘制已通过，无实际群消息发送。QQ 图片送达与主动播报权限仍待实机验收。已有玩家查询的全量图片迁移、物品和 Boss 功能尚未在本阶段实施；README/checklist 保持不变。

## 14. 物品查询阶段进度

已实现 `/item 名称`、`/item pve 名称`、`/item pvp 名称`、`/item 赛季 名称`、中文 `/物品` 和命名空间 `/tarkov item ...`。支持中文/英文全名、简称、多词名称与 `id:24位ID`；模式词开头的物品名可将整个名称加引号。另支持本次目录中的虚拟狗牌 ID `customdogtags12345678910`，其缩略图保持省略。名字不明确时先返回候选图片，按完整匹配、忽略大小写、包含匹配分级检索，包含匹配优先名称前缀/词首，保留总匹配数并列出前 25 件，须选 ID 或补充名称。
